## Independent recomputation (from committed `per_question`, not by calling the repo's metric code except where noted)

```python
import json
from scipy.stats import rankdata, beta

d = json.load(open("data/bench/results/p2-calibration-dev-v1.json"))
rows = d["per_question"]
probs  = [r["prob"] for r in rows]
labels = [float(r["label"]) for r in rows]
n_pos, n_neg = sum(l == 1 for l in labels), sum(l == 0 for l in labels)
ranks = rankdata(probs)
auroc = (sum(r for r, l in zip(ranks, labels) if l == 1) - n_pos*(n_pos+1)/2) / (n_pos*n_neg)
# -> 0.7816508644729504  (committed: 0.7816508644729504 — exact)

abstention_eval = [r for r in rows if not r["answerable"]]
errs  = sum(1 for r in abstention_eval if r["answered_at_tau"])
upper = beta.ppf(0.95, errs+1, len(abstention_eval)-errs)
# -> 0.018664699758660745 (committed: 0.018664699758660752 — agrees to 14 sig figs;
#    repo uses a 100-step bisection on the binomial CDF, not beta.ppf, so last-ULP
#    drift between the two independent numerical methods is expected)
```

## NEW findings

### N1 (minor) — `git_blob_sha()` doesn't verify the blob is actually reachable
`src/belge_gozu/answer/calibrate.py:710-724` (`git_blob_sha`), used at `cli.py:879,890`.

M4's whole point was to give the künye "a replayable reference, not prose" — a `git_blob` that
`git cat-file -p <blob>` can always restore. `git_blob_sha()` computes this with plain
`git hash-object <path>` (no `-w`, no reachability check). That call **hashes local file content
the same way whether or not the content is actually a committed git object.** Verified empirically:

```
$ echo "uncommitted probe" > /scratch/probe.txt
$ git hash-object /scratch/probe.txt
3ddbfb98eb39bc03430f3fc6a02fc7ae38735e7e
$ git cat-file -p 3ddbfb98eb39bc03430f3fc6a02fc7ae38735e7e
fatal: Not a valid object name 3ddbfb98eb39bc03430f3fc6a02fc7ae38735e7e
```

For **this** run the promise holds — I confirmed the worktree's `abstention_eval_v1.jsonl`/`retrieval_eval_v1.jsonl`/
`splits_v1.json` hash to exactly the blobs already committed at HEAD — but nothing in
`_calibration_setup` checks that the file is clean/committed before hashing it. If `calibrate fit`
is ever run against a locally-edited-but-uncommitted data file (a real scenario: the fix report's
own §M4 narrative describes a parallel drafter mutating `abstention_eval_v1.jsonl` uncommitted during this
very task), the künye would silently record a syntactically-valid-looking 40-hex `git_blob` that
`git cat-file -p` can never resolve — the exact "prose masquerading as a replayable reference"
failure M4 was fixing, just moved one layer down. The existing test only asserts
`len(git_blob) == 40` (`tests/answer/test_calibrate.py`), which can't catch this — and structurally
couldn't, since the CLI test fixture writes retrieval_eval/abstention_eval/splits into ephemeral `tmp_path` files
that are never `git add`ed, so `git_blob_sha` is already exercised only in its "always returns a
plausible hash that means nothing" mode there. Not a regression (the mechanism is new in this fix,
not previously present), and not a defect in the committed record under review — just a latent gap
in the new mechanism. **Suggested fix:** either `git hash-object -w` (force-write so the blob is
always resolvable regardless of commit status) or a `git cat-file -e <hash>` reachability check that
falls back to a `"git_blob": "uncommitted"` + explicit warning when the working tree is dirty for
that path.

No other new defects found in the changed code paths.
