# Findings, severity-ranked

## MAJOR

### J1 — The shipped threshold's `risk: 0.0` carries no uncertainty, and rests on 4 rows
`src/belge_gozu/answer/calibrate.py:409-447` (`choose_threshold`), `:838-842` (thresholds dict),
`src/belge_gozu/cli.py:1004` (echo).

`choose_threshold` maximises coverage subject to **empirical** `risk ≤ max_risk` with no guard on
how many rows that empirical risk is measured over. In this run the feasible set is exactly the
top-4 zero-error prefix, and the artifact records `"risk": 0.0` at `coverage: 0.023`. Measured from
the reconstructed data:

```
cov 10/173  risk 0.400   tau 0.3905
cov  8/173  risk 0.375   tau 0.4364
cov  6/173  risk 0.333   tau 0.4844
cov  5/173  risk 0.200   tau 0.4871   <- next point down
cov  4/173  risk 0.000   tau 0.5381   <- SELECTED
```

`0/4` has a 95% Clopper-Pearson upper bound of **0.527**. The number written into the artifact and
printed by the CLI as `risk=0.000` is, statistically, indistinguishable from 50% risk. One row moving
flips the operating point (the 5th-ranked row is a negative).

What makes this a Major rather than a nit is the **internal inconsistency**: this module already
established exactly this principle for the *other* threshold — `conformal_candidate` (`:450-490`)
refuses to write a number when `n` is too small, on the stated grounds that *"boş bir garantiyi eşik
diye artefakta yazmak, tam da kalibrasyonun önlemesi gereken sessiz yanlışlıktır"* (`:461`). That
guard protects the candidate that was **not** chosen, while the candidate that actually ships has
none. The report does say the fit is "kırılgan" (§6.2/6.3) — but prose in a `.md` is not the same as
the artifact refusing to overstate itself, which is this module's whole thesis.

**Scenario.** T8 wires `load_calibrator` into `/ask`. A future reader opens `calibrator.json`, sees
`thresholds.chosen.risk = 0.0`, and reasonably reports "measured 0% risk at the operating point".
It is not measured; it is 0-of-4.

**Fix (cheap).** Add `n_answered` and `risk_upper_95` (reuse `clopper_pearson_upper_bound`, already
in `calibration_metrics`) to `ThresholdChoice`/`to_dict()`; optionally require
`risk_upper_95 ≤ some bound` or a minimum `n_answered` in the feasibility filter, and mirror the
existing yellow "KIRILGANDIR" CLI warning when it is small. Before the phase-end gate run, so the
gate artifact carries the CI.

## MEDIUM

### M2 — Two behaviour-bearing literals live in function bodies and escape the fingerprint
`src/belge_gozu/retrieval/text.py:133` and `:312`.

`recipe_fingerprint()`'s stated contract is that it captures the **values** of recipe constants
automatically and leaves only **algorithmic form** to the manual `RECIPE_VERSION` bump
(`:180-188`). Two values are on the wrong side of that line:

1. `tr_lower()` — `s.replace("İ","i").replace("I","ı").lower()` (`:133`). This is a substitution
   table, not a shape. Changing it re-tokenizes every query and every page.
2. `extract_doc_name_tokens()` — the title gate `("KANUN" in ln or "ANAYASA" in ln)` (`:312`).
   Changing it changes `doc_names` → `routed_docs` → the **`routed` feature**, `route_window`, and
   therefore `served_top1` *and* the top-5 label.

Either edit produces a materially different recipe with an **unchanged fingerprint**, so a stale
calibrator would load without complaint — precisely the failure the key exists to prevent. Note the
commit itself hoisted `len(t) > 1` into `MIN_TOKEN_CHARS` for exactly this reason, with the comment
*"gövdede gömülü bir literal sessizce değiştirilebilirdi"* (`:58-61`). The same argument applies to
these two and was not followed through.

**Fix.** Hoist to `_TR_LOWER_MAP` / `_TITLE_KEYWORDS` module constants, add to the recipe dict, add
two parametrize cases.

### M3 — §5.3/§5.4 numbers exist only in the `.md`, and the repo's own `auroc()` cannot produce them
`p2-t5t6-report.md:210-227, 239-243`; `src/belge_gozu/bench/calibration_metrics.py:40-41`.

The per-feature univariate AUCs and the correlation matrix are the evidence base for §5.4's
collinearity argument and §6's fragility statement, but they appear in no committed artifact.
Worse, they cannot be regenerated with the project's own metric: `auroc()` calls
`_check_probs_labels`, which raises `ValueError: probs [0,1] aralığında olmalı` on raw features
(`served_top1` ranges 4.36–66.68). I confirmed this by calling it. They must have come from an
ad-hoc script that is not in the repo.

I reproduced all eight numbers independently (Mann-Whitney via `scipy.stats.rankdata`) and **they
are all correct to 4 decimals** — this is a reproducibility gap, not an accuracy problem.

**Fix.** Add a rank-based per-feature AUC to `feature_stats()` (it needs no `[0,1]` constraint, so it
belongs there rather than in `auroc`) so it lands in `kunye.feature_stats` and the claim becomes
self-evidencing.

### M4 — The committed run record cannot be reproduced with default flags
`data/bench/results/p2-calibration-dev-v1.json` (`kunye.note`), `src/belge_gozu/cli.py:799-802`.
