## ContextVar thread-safety assessment (priority spot-check, H1/M1)

**Safe.** `/ask` is a sync `def` route (`main.py:716`), so Starlette dispatches it via
`run_in_threadpool` → `anyio.to_thread.run_sync` → (inspected the installed anyio 4.x
asyncio backend source directly) `AsyncIOBackend.run_sync_in_worker_thread`, which does
`context = copy_context()` **on the calling (event-loop) thread** and hands that fresh
`Context` object to a pooled `WorkerThread`, which executes `context.run(func, *args)`.
Each request therefore gets an **independent copy** of the context; a `.set()` inside the
handler mutates only that copy, and the mutation is discarded when `context.run()` returns
— it never propagates back to the event-loop thread's ambient context, so it cannot leak
into the *next* job the same pooled worker thread picks up, nor into a sibling worker
thread handling a concurrent request (each has its own distinct copy). Verified this by
reading `anyio._backends._asyncio.WorkerThread.run` and `run_sync_in_worker_thread` source
directly (not from memory) — confirmed `copy_context()` + `context.run(...)` are exactly
what's used, which is the documented reason Starlette moved to anyio-based threadpool
dispatch (to make contextvars propagate correctly and in isolation).

Belt-and-suspenders: `verify.py:659,669,683` (`client_attempts(client) - before`) uses a
**delta**, not an absolute read, so the accounting is correct even if two rotation attempts
within the *same* call and even if the CLI's single-threaded run never resets the
ContextVar across questions (confirmed by grep — no `_API_ATTEMPTS.set(0)`/reset call
anywhere; the design doesn't need one). The delta trick's correctness still *depends* on
true per-request isolation to avoid cross-request interleaving corrupting the subtraction
— which the anyio/Starlette mechanism above provides.

**Rotation double-count (R36):** confirmed both by test and by tracing the real code path.
`gemini.py:527-566` (`RotatingGeminiClient._run`): slot 1 always calls
`first.client._generate(..., max_attempts=1)` (1 attempt, counter+1 at `gemini.py:361`
inside `_generate`'s own loop); on failure + rotation, slot 2 calls
`second.client._generate(..., started=started)` (up to `GEMINI_MAX_ATTEMPTS=2` more
attempts). `_API_ATTEMPTS` is one module-level ContextVar shared by both `GeminiClient`
instances (both slots), so one `generate_json()` call that rotates is measured as exactly
2 attempts via the before/after delta — `tests/answer/test_verify.py::test_budget_counts_api_attempts_not_verifier_calls`
locks this (`RotatingStub` simulates `_attempts += 2`, asserts `v.attempts == 2`,
`budget.used == 2`), and the live probe in `p2-t1t2-report.md` §"Canlı bütçe-tavanı
sondası" independently measured the same thing in production (a real key1→key2 rotation
during the answerer call, `detail.llm.rotations=[...]`).

## NEW findings

### N1 (Low) — `VerifierBudget`'s "SERT tavan" (hard cap) can overshoot by up to 2 attempts
`verify.py:647` checks `budget.exhausted` (a `>=` comparison) **before** starting a call whose
actual cost (1-3 attempts, depending on whether/how much the rotation ladder fires) is only
known **after** it returns (`verify.py:669,683`, `charge(attempts)` at `verify.py:515-517`).
Concretely: if `budget.used == max_attempts - 1` (i.e. `remaining == 1`, not yet exhausted),
the gate still lets one more claim through, and that single `verify_claim` call can spend up
to 3 real attempts (1 on the first key + up to 2 on the second after rotation) before the
budget is charged — so `budget.used` can end up at `max_attempts + 2` in the worst case (e.g.
12 actual attempts against a configured cap of 10). This is a check-then-act race against a
variable-cost action, not a concurrency bug — it will happen deterministically whenever the
last permitted call happens to rotate. It is **much** better than the pre-fix state (H1: fully
unbounded, up to 8×3=24 attempts per request with zero cap) and is bounded/request-scoped, so
it does not reopen H1 or justify blocking `BG_GATE_VERIFIER=true`. It does mean the docstring's
"SERT tavan" (`verify.py:488`) and "tavan hiçbir koşulda ALTTAN sayılmaz" framing slightly
overclaims precision in the *upward* direction (never undercounts, as documented; can
overcount past the configured ceiling by ≤2). **Suggested fix (optional, not blocking):**
either accept and document the slack explicitly ("cap is soft above the boundary by up to one
rotation's worth of attempts"), or make `EvidenceGate.evaluate` check `budget.remaining <
DEFAULT_VERIFIER_MAX_ATTEMPTS_PER_CALL` (i.e. reserve headroom for the worst-case single-call
cost) before allowing one more claim through.
